Research synthesis

What ArchiveTune actually solves.

Its advantage is not a magic API call. It is a complete native pipeline with typed data, resolver state, expiry handling, and a real media service.

Catalog is a domain, not DTO plumbing

Search, home, explore, charts, moods, genres, artists, albums, playlists, related tracks, queues, and continuations are typed and rendered as sections/entities. The UI does not need to understand raw InnerTube JSON.

Playback is a resolver subsystem

Player responses, client profiles, player JavaScript, signature and n transformations, PO tokens, headers, expiry, fallback clients, and re-resolution are coordinated before Media3 sees a URL.

Device state is durable

Room/DataStore own history, queue, library, lyrics, downloads, settings, and resolver cache metadata. The app does not ask a remote backend to remember how its player works.

MediaSession owns the experience

A foreground service owns queue transitions, notification metadata, lockscreen controls, seeking, preloading, audio focus, process death, and recovery.

ArchiveTune repository and dependency map verified from source

core

Active Git submodule. Owns InnerTube client contexts, requests, typed parsing, auth/session state, and catalog/playback contracts. It integrates NewPipe Extractor for stream extraction and cipher support.

morideobfuscator

Active Git submodule. Its JavaScript module uses youtubei.js player analysis/extraction in a Kotlin QuickJS worker; the Android app separately owns the BotGuard/WebView PO-token lifecycle.

lyrics and IconPack

Active Git submodules for provider-based lyrics and community icon assets. Lyrics are split into provider modules rather than being a single catalog API.

Other product modules

lastfm, canvas, shazamkit, and spotifycore are included Gradle modules in the app repository. Media-control source also references Moriafly/media-kit and FlamingoSank; these are source-provenance references, not active Gradle dependencies.

Separate reference, not an ArchiveTune dependency

LuanRT/BgUtils is a useful independent MIT PO-token reference. Its current example fetches an InnerTube attestation challenge and interpreter, then uses BotGuardClient and WebPoMinter in a browser-like runtime. It requires successful runtime attestation and is not a drop-in Android or QuickJS provider. It is not listed as an ArchiveTune submodule or dependency; ArchiveTune source contains its own Android WebView BotGuard lifecycle.

Execution map

Six milestones, one reliable cutover.

These are intentionally broad outcomes. Smaller tickets belong inside them; completion is defined by observable gates, not calendar estimates.

01Standalone InnerTube catalog core
Search, home, explore, details, and continuations work with the backend unavailable.PASS: baseline

Build

  • Native Kotlin core for Ktor/OkHttp, JSON, compression, client contexts, locale, retries, and continuations.
  • Typed models for tracks, artists, albums, playlists, sections, browse pages, filters, suggestions, queues, lyrics entry points, and region state.
  • Migrate MusicRepository from MoodifyServerApi to native repositories with cache-first refresh.
  • Add fixture parser tests and live smoke tests for search, artist, album, playlist, browse, and continuation.
Exit criteria

MOODIFY_SERVER_URL may be blank or invalid. Android still searches, opens details, loads discovery, paginates, and never shows N/A where InnerTube has valid data.

02Native playback resolver and recovery
Direct device playback with player-script analysis, token binding, fallback clients, and re-resolution.PARTIAL: live matrix

Build

  • Player response retrieval with consistent visitor/session state.
  • Player JavaScript identification, versioned cache, sandboxed deciphering, signature and n transformation, and runtime prewarming.
  • PO-token state tracked by type, client, video/session binding, source, and expiry.
  • ResolvedAudioStream contract containing URL, headers, format, bitrate, expiry, client profile, and token binding.
  • Controlled 403/410 recovery and audio-only format selection. No artificial chunking.
Exit criteria

Playback passes the backend-blocked device matrix. Seeking does not restart. Lock-screen playback works. Expired or forbidden streams trigger controlled re-resolution rather than endless retries.

03Durable local state and MediaSession
Queue, history, library, lyrics, notification, and recovery survive process changes.PARTIAL: device proof

Build

  • Room for entities, queue, history, library, lyrics, artwork, and resolver cache metadata.
  • DataStore for region, language, quality, cache, theme, and feature flags.
  • Single MoodifyPlaybackService owner for Media3, MediaSession, notification, transitions, position persistence, and callbacks.
  • Next-track preloading, audio-focus recovery, network loss handling, process death restoration, and cache invalidation.
Exit criteria

Restart restores queue and position. Notification and lockscreen controls are real. Next track is smooth when preloading succeeds, and recovers when it does not. Download/offline acquisition is deferred and does not block this gate.

04ArchiveTune-style catalog experience
Moodify becomes a typed, region-aware YouTube Music catalog instead of playlist-shaped mood tiles.PARTIAL: product depth

Build

  • Native home, explore, charts, new releases, moods, genres, quick picks, and region-aware shelves.
  • Shared section renderer for mixed shelves, entity rows, albums, playlists, and search filters.
  • Rich artist, album, playlist, related, up-next, and queue surfaces with continuation loading.
  • Mood worlds map explicitly to playlist IDs, browse IDs, charts, genres, or generated queues.
  • Local deterministic personalization from history, likes, pinned playlists, and continue listening.
Exit criteria

A first-time user sees useful content without seeded Moodify playlists. Every card has a typed source, opens a working destination, and plays through the same canonical track identity.

05Lyrics, library, and optional integrations
The app feels complete without making optional features part of the playback core.PARTIAL: providers

Build

  • Native transcript/lyrics plus LRCLIB behind provider interfaces, synced parsing, translation, caching, and seek alignment.
  • Liked tracks, saved albums, local playlists, import/export, and artwork cache.
  • Optional interfaces for SponsorBlock, Android Auto, Cast, Shazam, Last.fm, Canvas, backups, and CSV export.
  • Account synchronization only after anonymous/local behavior is reliable. Download/offline acquisition and storage controls are explicitly deferred.
Exit criteria

Lyrics and local library work without the backend. Optional integrations can be disabled safely. Downloads are not part of this migration's acceptance gate.

06Cutover, verification, and release hardening
Evidence proves Android is standalone while the web backend remains healthy.PARTIAL: release proof

Build

  • Debug network audit that fails if Android calls Moodify during catalog, playback, lyrics, queue, or library operations.
  • Fixture tests, live smoke matrix, privacy-safe resolver metrics, and a diagnostic screen.
  • Bounded retries, backoff, cache expiry, no token/URL logging, and runtime prewarming.
  • Temporary native-vs-server flag only during rollout, followed by deletion of Android backend routes and config.
  • CI build, lint, instrumentation, release APK packaging, and physical-device verification.
Exit criteria

Backend can be stopped or misconfigured and Android still works. Web regression tests pass. A physical-device release APK completes the catalog/playback matrix.

06Resolver lifecycle and stream selectionPlayer response → transforms → token binding → expiring stream.
Select client profile. Use an ordered, instrumented profile list; separate catalog clients from playback clients and honor region/session capabilities.
Fetch player response. Send videoId, visitor/session context, client version, playback context, and required token material through the native client.
Ensure player JS. Detect the player version, load a verified cached bundle, or fetch and analyze the new player script inside the sandbox.
Transform formats. Apply signature and n transformations only in the JS runtime; validate the transformed URL before returning it.
Resolve PO-token state. Reuse only a token with matching type, client/session/video binding, and unexpired validity.
Select audio. Prefer supported audio-only formats by policy: codec/container compatibility, bitrate, loudness/quality, and size constraints.
Return immutable result. Include URL, headers, mime, codec, bitrate, content length if known, expiresAt, client profile, token binding, and resolver version.
CacheCache player analysis, not durable raw media URLs. Keep stream results memory-scoped and expiry-aware.
SecurityRedact URL query strings and token values from logs and crash reports.
FailureClassify no-format, transform, token, consent, bot, HTTP, and parser failures separately.
07Seek, buffer, 403/410, and network recoverySeeking is a transport concern; expiry is a resolver concern.
Normal seek. Media3 issues a range request against the same valid stream; service keeps the queue and media item stable.
Detect failure. Classify HTTP 403/410, EOF, timeout, connection loss, unsupported container, and decoder error before deciding recovery.
Capture position. Save the requested position and queue index before replacing the media source.
Invalidate only what is stale. Remove the stream result for that video/client; do not wipe the player-script cache or all session state.
Re-resolve once. Refresh session/token state if needed, select a fallback client, and return a new stream result.
Resume. Prepare the replacement source at the saved position; if it fails again, stop retrying and expose a diagnostic error with retry action.
Transport ruleDefaultHttpDataSource/DefaultDataSource; no 512 KB artificial truncation.
User experienceKeep artwork/title/queue visible during recovery; show buffering only while work is active.

Reality check

The hard part is not the catalog.

Playback resolver maintenance is the main technical risk. The plan treats it as a subsystem with tests and observability.

RiskWhy it mattersMitigation
YouTube client changesWorking client profiles can change without notice.Isolate profiles, use fixtures/live smoke tests, classify failures.
PO-token and BotGuard changesResolution can work on one device and fail on another.Bind token state to client, video, and session; refresh and back off.
Player JavaScript changesCipher logic can invalidate streams.Cache by player version and run analysis in a sandboxed runtime.
Expiring CDN URLsA stream URL is not a durable media ID.Store expiry, invalidate on 403/410, and re-resolve once.
Scope growthArchiveTune parity can consume the reliability budget.Keep integrations behind interfaces and gate them after core acceptance.
GPL-3.0 sourceDirectly copying code creates licensing obligations.Reimplement from observed architecture or make a deliberate compliance decision first.
